# 判据变更登记 · P05（`why` 字段长度判据）

> 变更人：主 Agent　时点：2026-10-15　触发：D2 子 Agent 在执行 P05 时报出的口径冲突
> 性质：**契约缺陷修正**，⛔ 不是"为通过而放宽阈值"

## 1. 触发事实（D2 实测）

| 项 | 实测 |
|---|---|
| `complete` 节点 `why` 非空白字符数 | PE-F-01 **186** / PE-R-02 **206** / PE-P-02 **203** |
| 原契约上限 | 120 |
| 全量口径（caliber = 汉字 + 拉丁词） | `complete` 171 / 183 / 185；`registered` 114–206 |
| 越限节点数 | **67 / 67**（即全部） |
| 边界从句内联于 `why` 的节点数 | **67 / 67** |

## 2. 根因（两层，均为契约侧）

1. **强制要求与字段供给不匹配**：本契约在委派与正文里都强制「每个节点须写出适用边界」，但字段表里**没有 `boundary` 字段** ⇒ 边界只能被写进 `why`。
2. **上限阈值无因果依据**：`why 80–120` 是契约初稿**凭直觉定的**，不是从任何可度量目标推导出来的（既非可读性实测，也非版式约束）。按 `criterion-design-validation` 与需求层 `CRITERIA.md` 的纪律——**「阈值不得由规模直觉推导」**——该阈值本身即缺陷。

**第三层（自检盲区）**：D1 的 `10-dag-data/_selfcheck.py` 的 `C28b` 只断言了 `intro ≤250` 与 `summary ≤80`，**没有断言 `why` 的上限** ⇒ 越限在数据侧**结构性不可见**，直到 D2 在产物侧撞上才暴露。

## 3. 裁决：改契约，不改数据

**为什么不做数据拆分**：实测机械拆分（按边界关键词切句）**不可靠**——`PE-F-03` 的「…而是边界：」是**主题词**而非适用性限定，被正则误捕；`PE-P-02` 真正的边界句（「在能力较弱的模型或需要严格流程合规的场景下…」）反而未被捕获。机械拆分会**降低内容质量**。逐节点人工改判属内容波次工作，登记为第 2 轮任务。

| # | 变更 | 依据 |
|:--:|---|---|
| C1 | **下限保留为硬判据**：`complete` caliber ≥80、`registered` ≥60 | 因果直接：防"一句话打发"，与"讲清为什么需要"这一用途对齐 |
| C2 | **上限 120 撤销，改为报告项（⛔ 不判 FAIL）** | 导语过长只影响版式首屏，与正确性无关；**无因果依据可定硬阈值** ⇒ 按纪律应换判据而非改数字。报告项使实测值仍逐条可见，⛔ 不是"隐藏" |
| C3 | **新增 `boundary` 字段**：本轮可选、第 2 轮起必填 | 让"每条技巧配适用边界"从**子串关键词探测**升级为**一等受检对象**；本轮保留内联形态，⛔ 不做机械拆分 |
| C4 | **口径写死**：`caliber = 汉字数 + 拉丁词数`（正则见 SCHEMA） | 消除"字"的歧义（字符数 / 字节数 / 非空白字符数三种读法差 30%+），使判据可复现 |
| C5 | **补齐自检盲区**：`why` 下限与上限实测值须在门控与自检中逐条打印 | 堵住"越限结构性不可见"这一层 |

## 4. 变更后的实测读数（对现有数据，⛔ 未改一个字节的数据）

| 判据 | 结果 |
|---|---|
| `why` 下限（硬） | 全部通过：`complete` 最低 171（≥80）· `registered` 最低 114（≥60） |
| `why` 上限（报告项） | 实测区间 114–206 caliber，逐条打印；⛔ 不产生 FAIL |
| `intro` / `summary` | 未变（仍按原判据） |

## 5. 第二例（同型缺陷）：`summary` 数值下限

**触发**：D2 在实现新口径时逐节点复算，发现 `summary caliber ≥30` 下 **49 个节点跌破**（48 个 registered，最低 PE-S-04 = 23；含 `complete` 的 PE-P-02 = 29），而它在数据侧无权修改。

**根因（与第 2 节同型）**：原 `summary ≥30` 是在**旧单位（`len()` 字符数）**下标定的（旧单位下实测最低正好 30、全绿）；本契约引入 `caliber` 单位后，该数字**未重新标定**即被沿用 ⇒ 新单位下无因果依据。

**★ 处置：换判据，⛔ 不是改数字**。D2 提出的三个选项（整体降为报告项 / 按实测最低 23 定 ≥20 / 保留硬判据如实出红）**均被否决**：
- 整体降为报告项 ⇒ 连"防一句话打发"一起丢掉；
- 按实测定 ≥20 ⇒ 让阈值迁就数据；
- 如实出红 ⇒ 门控把 49 个**本无问题**的 summary 判失败（它们都是一句完整结论）。

`summary` 真正要保证的是「**它是一句完整、独立、非复制的结论**」——这与长度无关。故改为三条**结构性**硬判据：

| # | 新硬判据 | 防的失败模式 |
|:--:|---|---|
| 1 | 以句末标点（`。！？`）结尾的完整句 | 片段化（"很好" / "见上文"） |
| 2 | 不含空洞占位词 | 占位式敷衍 |
| 3 | **不与 `why` / `intro` 的任一整句逐字相同**（整句归一化后比对，⛔ 非子串包含） | 复制粘贴当小结 |

`caliber` 实测值转为**报告项**逐条打印。

## 6. 由两例归纳的判据分档原则（第 2 轮起沿用）

> 数值阈值只在能说清「**把数据改成符合它会改善内容**」时才作硬判据；否则降为**报告项**（逐条打印，⛔ 不判 FAIL）。
> 判别句：*若把数据改成符合该阈值会**降低**内容质量，则问题在阈值不在数据。*

据此定档：

| 字段 | 保留的硬数值下限 | 理由 | 上限 |
|---|---|---|---|
| `why` | complete ≥80 / registered ≥60 | 防"一句话打发" | 报告项 |
| `intro` | registered ≥120 | 机制叙述需要展开空间 | 报告项（>250 打印） |
| `summary` | ⛔ 无 | 与长度无因果关联 | 报告项（>80 打印） |

**连带统一**：`intro ≤250` 与 `summary ≤80` 的上限一并降为报告项——上限只影响版式首屏，与正确性无关，与 `why` 上限同处置。

## 7. 残留与移交第 2 轮

1. **`boundary` 字段的拆分**：67 个节点须逐条人工改判（⛔ 不得用正则机械拆分）；完成后 `boundary` 由可选转为**必填**，并把 `why` 主体压回其目标带。
2. **`why` 上限的再定**：第 2 轮应在**真实版式**（一屏可读量实测）下重新推导，而不是再次凭直觉给数。届时若浏览器验证通道可用（本会话不可用，见 `VERIFY-CONSTRAINT.md`），应取真实渲染读数。
3. **本条变更须回写第 2 轮的 SCHEMA 与门控**，并在 `PUBLISH-STATE.json` 的 gates 记录中保留本登记件的指针。

## 8. 纪律自陈

> 本变更的正当性来自**原阈值无因果依据**，而非"数据过不了"。判别标准：若把数据改成符合原阈值（120）会**降低内容质量**（因为必须砍掉适用边界），则问题在阈值而不在数据。本次正是这种情形——因此换判据（C2），并**同时补上原契约真正缺失的字段**（C3），而不是简单地把 120 改成 200。
