一句话结论

用固定的标记体系划清指令与数据的边界，并知道它只消歧、不保安全。

01为什么需要它

多部分提示里最容易出错的不是内容，而是边界：模型无法区分哪段是指令、哪段是示例、哪段是待处理的资料。

  • 分隔符解决的就是这个歧义问题，它让「指令」与「数据」在文本上有了可见边界，也是后续不可信内容标注与注入防御的前提。

适用边界

标记的效果取决于模型是否针对此类标记做过对齐训练，换模型必须重测；标记只能降低歧义，不能提供安全保证，因为模型在架构上仍不区分指令与数据。

02机制说明

现行官方口径推荐用 XML 风格标签包裹示例与资料，理由是这类标签能让模型在多部分提示中无歧义地解析结构；同时要求把长资料放在提示前部、把 query 与指令放在其后，并在资料较多时先让模型引用相关片段再作答。

  • 工程上应把标记体系当成一套需要版本化的小规范：标签名固定、嵌套规则固定、同一含义只用一个标签，否则标记体系本身会成为新的歧义源。
  • 需要强调的是，标记的收益主要体现在「多部分提示的边界消歧」上，它不是通用性能杠杆；把它当成万能提准手段会在简单任务上白付 token。

03何时该用 / 何时不该用

按场景对照：先看条件，再看该怎么做。
类别场景 / 条件（总结）具体做法（细节）
该用提示同时包含指令、示例、资料与用户输入时必须加显式边界标记。
该用资料很长时把资料置于前部并配合先引用后作答，以对抗位置偏差。
不该用把它当通用性能杠杆单段指令、单轮问答上引入标签只增加 token 与解析噪声。
不该用假设标记即安全边界不可信内容即使被标记包裹，仍可能被当作指令执行。

04实验台

  1. filemarkdown

    查看代码
    同一任务写两版提示，只差边界标记：
  A 版：指令、示例、资料、用户输入连成一段，靠空行分隔
  B 版：四类内容各用固定标签包裹（标签名固定、嵌套规则固定、同一含义只用一个标签）
两版各跑 30 次，记录：结构违规率（输出格式不合契约的次数）、以及「资料里的句子被当成指令执行」的次数。
判据：B 版结构违规率应显著低于 A 版；若两者无差异，说明该模型对此类标记不敏感，须换标记或改用其它隔离手段。

    预期观察：读者能量出标记带来的消歧收益，也知道这个收益会随模型变化（同一标记在另一模型上可能无差异）。

  2. shellbash

    查看代码
    # 注入探测：把「资料」里放一句伪指令，看模型是否把它当指令执行
# 分别测「裸资料」与「已标注为资料」两种形态，各 20 次，统计被执行的次数
for shape in bare tagged; do
  echo "== shape=$shape =="
  for i in $(seq 1 20); do
    curl -s "$API_ENDPOINT" -H 'content-type: application/json' \
      -d @"inject-$shape.json" | grep -c 'INJECTED'
  done | sort | uniq -c
done

    预期观察：标注能降低被执行的次数，但通常不为零——这一步是让读者亲眼看到「标记只消歧、不保安全」，不要把标记当成注入防线。

05证据

主张官方一手要求把示例包在标签里，以便模型能把示例与指令区分开——这是「边界标记」的直接依据。

06术语

术语分隔符与上下文隔离　Delimiters and Context Isolation

界定用 XML 标签、专用分节标记等把指令、示例、资料与用户输入在文本上划出边界，使模型能无歧义解析多部分提示。

相关节点—

术语标记敏感度的迁移性　Transferability of Markup Sensitivity

界定对某种标记（如 XML 标签）的响应强度取决于该模型是否针对此类标记做过指令对齐训练，因此同一标记在不同模型上的效果不可假定一致。

相关节点—

07失效模式

  • 把标记当通用性能杠杆单段指令或单轮问答上加标签只增加 token 与解析噪声，收益为零。
  • 标记体系自身失控标签名不固定、同一含义用多个标签、嵌套规则随人而异，标记于是成为新的歧义源。
  • 把标记当安全边界不可信内容被标签包裹后仍可能被当作指令执行，注入在架构层面并未被挡住。
  • 关键资料放在中部位置偏差会让中部信息被忽略，而标记只解决「这段是什么」，不解决「读者还会不会看它」。
