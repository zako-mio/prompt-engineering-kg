# G05 评测与自动优化

- 英文名：Evaluation and Automatic Optimization
- 分区序号：5
- 组内节点：9 个（已写满 9）
- 层范围：第 10 – 21 层

## 本组导读

本组先立判据再谈优化：没有评测集，任何「提示词变好了」的判断都不可复现。内容包括评测集构造与判据设计、模型即裁判的偏差、评测工具链与红蓝对抗，再向上走到自动提示词工程、声明式编译与签名、文本梯度与反思式进化、元提示，最后落在提示词版本化与回归。读者学完应能先回答「怎么知道变好了」，再决定是否引入自动优化，并知道自动优化的收益前提是执行轨迹可获取、评分函数可用。

## 本组学习路径

### 第 10 层

- PE-E-01 为什么必须先建评测集（Why Build an Eval Set First）

- 为什么在这层：PE-E-01 ← PE-C-04（PREREQ）检索质量的教训是「先度量再优化」，这正是评测集的作用

### 第 11 层

- PE-E-02 测试集构造（Test Set Construction）

- 为什么在这层：PE-E-02 ← PE-E-01（PREREQ）先建立评测集必要性，再谈如何构造才有区分度

### 第 13 层

- PE-E-03 模型即裁判及其偏差（LLM-as-a-Judge and Its Biases）

- 为什么在这层：PE-E-03 ← PE-E-02（PREREQ）确定性判据不够用时，才引入模型裁判并处理其偏差
- 为什么在这层：PE-E-03 ← PE-O-05（PREREQ）评估者的可靠性问题正是模型裁判的偏差问题

### 第 17 层

- PE-E-05 自动提示词工程（Automatic Prompt Engineering）

- 为什么在这层：PE-E-05 ← PE-E-02（PREREQ）自动优化依赖评测集与可自动计算的判据
- 为什么在这层：PE-E-05 ← PE-R-08（PREREQ）反思给出候选改进，自动提示词工程把候选筛选机制化

### 第 18 层

- PE-E-06 声明式编译与签名（Declarative Compilation and Signatures）

- 为什么在这层：PE-E-06 ← PE-E-05（UPGRADE）从「让模型改指令」升级为「声明签名并由编译器搜索配置」

### 第 19 层

- PE-E-04 评测工具链与红蓝对抗（Evaluation Toolchain and Red Teaming）
- PE-E-07 文本梯度与反思式进化（Textual Gradient and Reflective Evolution）

- 为什么在这层：PE-E-04 ← PE-A-06（FLOW）隔离措施是否有效只能靠对抗评测度量，故接评测工具链
- 为什么在这层：PE-E-04 ← PE-E-03（PREREQ）先理解裁判偏差，才能正确使用工具链中的模型辅助断言
- 为什么在这层：PE-E-04 ← PE-S-05（FLOW）校验器的判据与评测工具链的断言共用同一套表达方式
- 为什么在这层：PE-E-07 ← PE-E-06（PREREQ）先有编译流程与指标，再引入以反馈为梯度的优化方式

### 第 20 层

- PE-E-08 元提示（Meta-prompting）

- 为什么在这层：PE-E-08 ← PE-E-07（PREREQ）先能改进组件，再让模型生成或改写提示词本身

### 第 21 层

- PE-E-09 提示词版本化与回归（Prompt Versioning and Regression）

- 为什么在这层：PE-E-09 ← PE-E-04（PREREQ）工具链就位后，回归才有可执行的载体
- 为什么在这层：PE-E-09 ← PE-E-08（PREREQ）批量改写产生大量候选，必须有版本化与回归来筛选
